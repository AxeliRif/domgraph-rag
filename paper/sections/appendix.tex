\section{Compute budget for contrastive fine-tuning}
\label{sec:appendix-gpu}

Estimated from the training loop's structure (\S\ref{sec:contrastive}), not measured: at batch size 4, $n{=}2$ hard negatives, 3 epochs over the 534 examples of Table~\ref{tab:dataset-stats}, one optimizer step embeds 4 questions and 12 tile images; the current implementation calls the model once per question and once per image rather than as a single batched forward pass, so one step costs 16 sequential forward passes through \texttt{Qwen2-VL-7B-Instruct}, and a full run costs $402$ steps $\times$ 16 $=$ 6{,}432 forward passes, all contributing to one shared backward per step. Weights alone are $\approx$14\,GB in \texttt{bfloat16}; LoRA keeps the optimizer state small, but activation memory scales with the frozen base model's forward/backward graph across all 16 unbatched calls held simultaneously before the shared backward. We expect a single 40--80\,GB datacenter GPU (A100/H100 class) to suffice at this dataset size -- no multi-GPU training is warranted -- sized conservatively until peak memory is profiled, since the vision encoder can still emit a large token count for our largest tiles ($2048\times2048$\,px) before its own internal resizing caps it. At an assumed 150--400\,ms per forward call, the 6{,}432 calls total 16--43 minutes of forward compute alone; including backward and the overhead of 16 unbatched calls per step, we would not be surprised by anything from under an hour to several hours wall-clock for the full run. Batching \code{embed\_questions}/\code{embed\_tiles} into one padded forward pass per step is the highest-value change before renting GPU time, reducing both the estimate and its uncertainty; we flag it as the next engineering step rather than fold an unbatched-loop number into a claimed result.

 & Tiles/page & Px/tile & Total px/page \\
\midrule

Grid & 4.9  & 2{,}081{,}117 & 10{,}174{,}350 \\
\bottomrule
\end{tabular}
\caption{Tiling cost, same 18 pages as Table~\ref{tab:tiling-ablation}. DOM-guided tiling produces more, smaller tiles, yet a smaller \emph{total} pixel budget per page (2.7$\times$ less) -- a direct consequence of the text-flow bounding-box measurement of \S\ref{sec:tiling}, which crops text tiles to the width their content actually occupies instead of the full page width every grid band uses regardless of content. If image tokens scale with pixel area, as they do for \texttt{Qwen2-VL}'s vision encoder, DOM-guided tiling need not trade accuracy for token cost against a blind grid.}
\label{tab:appendix-tiling-cost}
\end{table}

Attach rate (the fraction of questions whose answer string survives a tiling's 200-character text preview) is 52.5\% for DOM (223/425) against 27.1\% for grid (115/425) -- consistent with grid bands aggregating far more raw content into the same fixed text budget, diluting the specific snippet a lexical scorer needs to surface.
